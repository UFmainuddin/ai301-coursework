# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-grounded-in-evidence | The plan's stated cause/diagnosis, read directly against every artifact in the package's repro evidence (control runs, before/after steps, timing or output comparisons) — not against what the issue thread believes or how confidently the plan is written | No artifact in the repro evidence contradicts or rules out the stated cause. A diagnosis is an inference explaining the evidence (what regressed, what a control isolated, what a cache/version delta showed) and does not need to be directly observed to pass — it only needs nothing in the evidence to rule it out. If a control run or comparison in the evidence actually isolates a different mechanism (the behavior persists with the blamed mechanism held constant, or is absent with it unchanged), this fails regardless of confidence or thread consensus. | required |
| bounded-scope | The plan's in-scope/not-in-scope statement and the files or areas it names, read against what the issue itself asks for | Every named change is required to fix the issue. Explicitly narrowing scope (deferring extra work, gating a fix to one platform, splitting out an unrelated symptom) with a stated reason still passes — that is bounding, not creep. A plan that adds a rewrite, migration, new option, cross-cutting refactor, or other "while I'm in there" work the issue never asked for fails, even if the core fix buried inside it is correct. | required |
| executable-plan | The plan's named files/locations and chosen approach, read for whether a stranger could start work without asking the author anything | The plan names a specific subsystem/file area and one chosen approach (not a choice between several). Naming the exact function or line is not required if the plan has already demonstrated, concretely, how it will be pinned down (for example, debug output that already shows where) — that is a narrowing step, not an open decision. A hedge between multiple candidate approaches or locations ("upstream or vendored, whichever is easier", "somewhere in the middleware", "maybe also check X") with no chosen path fails. | required |
| decisive-test-plan | The plan's test plan, read against the repro evidence's own steps and artifacts | The test plan names a specific, observable outcome tied to the repro evidence — typically re-running the repro steps and naming the expected changed result. Naming only "run the full test suite" with no outcome specific to this fix, or a subjective/non-observable outcome, fails. | required |
| honest-uncertainty | The plan's stated risks, unknowns, and deferrals, read against what the plan claims to know or have settled | Unknowns and deferred work are named as such, with a reason. A plan that asserts something as settled or certain that the repro evidence doesn't establish, without flagging it as a risk or unknown, fails. | required |
| thread-and-convention-aware | The plan comment, read against the issue thread's highlights (explicit maintainer direction, related open work) and the repo-facts block's stated conventions and AI-disclosure policy | The comment engages with explicit maintainer direction or clearly related existing work in the thread rather than ignoring it, and discloses AI assistance if the repo's stated policy requires disclosure. Ignoring explicit maintainer direction present in the thread, or omitting AI-use disclosure the repo's policy requires, fails this check regardless of how good the plan itself is. | required |

## Verdict rule

Accept only if every required check grades `pass`. Any required check graded `fail` or `unclear` holds the package (verdict `reject`). There are no `preferred` checks in this rubric — a plan that is wrong on any one of these families (a diagnosis the evidence contradicts, scope that creeps past the issue, a plan a stranger can't start from, a test that proves nothing, false certainty, or a comment that ignores the thread or the repo's own rules) is not ready to post or build from. `unclear` on any required check is treated as `fail`.
