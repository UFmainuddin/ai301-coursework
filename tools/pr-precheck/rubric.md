# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | Every changed file/hunk in the diff, read against the plan's stated scope, boundary, and any deviation notes; the PR description's fidelity claims ("implements the plan exactly", "no changes beyond X"), read against what the diff actually contains | Every changed file or hunk falls inside the plan's stated scope, or is covered by an honest deviation note (in the plan and/or the description). The description's claims about what the PR does match the diff exactly — neither claiming more than the diff delivers nor staying silent about something the diff adds beyond the plan. A diff that adds an unplanned change with no deviation note (more than planned), or a description that claims something the diff doesn't actually contain (less than planned), fails — regardless of how good the core fix is. | required |
| test-evidence | The PR's test-evidence section, read against every distinct observable outcome the plan's test plan names, and against the repo's own stated checks | The plan's primary repro/outcome is shown with a specific, observable before/after tied to the exact failing path the issue and plan name — not a different or unchanged code path, and not merely asserted ("tests pass", "verified working"). Every other outcome the plan's test plan names is at least concretely addressed — a quoted assertion, a named control's stated result, or its own transcript — rather than left completely unmentioned. The repo's own stated checks are named specifically (the exact command, e.g. `go test ./pkg/x/...`, not a vague "tests pass") with their result stated; a full output dump or test count strengthens this but is not required on its own — a named command plus a stated passing result is sufficient. A secondary outcome the test plan named but the evidence never mentions at all fails this check, even if the primary outcome is shown well. | required |
| diff-quality | The unified diff and the commit list | Every hunk in the diff is part of the stated fix. No debug prints, commented-out code, dead functions, pure formatting/reindent churn, or unrelated edits ride along — even when they're clearly left over from development rather than malicious, and even when the core fix itself is correct and well evidenced. | required |
| standards-and-comms | The repo-facts block's stated PR-template sections and contribution/AI-disclosure policy, read against the PR description's actual content; the thread's explicit maintainer direction, read against whether the description engages it | Every section the repo's PR template requires has real, specific content (not boilerplate or left empty), any repo-specific required items (a linked issue number, a checklist, a changelog/whatsnew entry) are present, and AI-use disclosure is included if the repo's stated policy requires it. Where the thread shows explicit maintainer direction or an open question, the description engages it rather than ignoring it. A required template section, checklist item, or disclosure that's visibly missing fails this check regardless of how good the rest of the PR is. | required |

## Verdict rule

Accept only if all four required checks grade `pass`. Any required check graded `fail` or `unclear` holds the package (verdict `reject`). There are no `preferred` checks — a PR that is wrong on any one of these families (silent scope drift, evidence that doesn't decisively prove the fix, debris that makes the diff unreviewable, or ignoring the repo's own stated asks) is not ready to submit. `unclear` on any required check is treated as `fail`.

**Honest-outcome rule, carried forward from weeks 2 and 3:** a deviation or a deferred piece of work is not a fidelity failure when it is stated as such in the plan (its `## Deviations` section or scope) and consistently restated in the PR description — that is bounded honesty, not drift. `plan-fidelity` and `standards-and-comms` both read a disclosed shortfall as compliant, never as "less than everything, therefore hold."
