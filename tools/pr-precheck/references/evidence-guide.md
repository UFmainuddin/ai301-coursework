# Evidence guide: where evidence lives in a PR package

## Plan fidelity (harness category: silent-drift)

**Where it lives.** In an eval bundle: the plan-context block's scope/boundary statement and any deviation notes, read against the candidate PR's unified diff (every changed file, every hunk) and its description's claims about what it does. In live mode: `plan.md` (including its `## Deviations` section), read against `git diff main...HEAD` on your branch and your draft PR description.

**What good looks like.** List every file and hunk the diff touches, then check each one against the plan's stated in-scope list. Every hunk should either be clearly part of what the plan named, or be covered by a deviation note that says so explicitly. A description's fidelity claim ("implements the plan exactly," "no changes beyond the fix") is itself evidence to check against the diff, not just prose: read the diff file by file against that claim. Silent drift runs both directions — a diff that quietly does *more* than the plan (an unplanned rewrite, a new config option, a drive-by rename) with no deviation note, and a diff or description that claims *more than the diff delivers* (a description saying docs were updated when the diff shows only the code change). A deferral that's named in the plan's own note and restated in the description — not snuck in silently — is honest scoping, not drift, and passes.

## Test evidence (harness category: not-tested)

**Where it lives.** In an eval bundle: the plan-context block's test plan (which may name more than one observable outcome) and the original repro evidence's exact steps, read against the candidate PR's test-evidence section. In live mode: your `plan.md`'s test plan and your unit-2 repro steps, read against your own re-run output and the repo's own check commands (`make test-unit`, `make lint`, `make typecheck`, etc.).

**What good looks like.** First check the plan's primary repro/outcome: is there a specific before/after transcript that exercises that exact path — not a different, adjacent, or already-working path? "Tests pass" or "verified working for a day" with no shown output is not decisive; a transcript showing the specific before (failing/wrong) and after (fixed) state is. Then check every other outcome the test plan names (a secondary scenario, a control that should stay unchanged, a warning that should still print): each one needs to be at least concretely addressed — a quoted assertion from a named test, a one-line stated result for a control, or its own transcript — not full silence. The line between "concretely addressed" and "not tested" is whether a specific result is named for that outcome at all, not whether it gets its own full transcript: pointing at an added test's exact assertion line is decisive even without separately printed output, but a test-plan item the evidence never mentions in any form is not tested, even when the primary fix is shown perfectly. For the repo's own stated checks (lint, typecheck, unit tests), what matters is naming the specific command that was run (e.g., `go test ./pkg/minikube/machine/... ./cmd/...`, not a bare "tests pass") together with its result; a full transcript or a test count makes it stronger but isn't required by itself — a named command with a stated passing result is enough to count as run, as opposed to an unnamed, generic claim that nothing was actually run against.

## Diff quality (harness category: unreviewable)

**Where it lives.** In an eval bundle: the candidate PR's unified diff and commit list. In live mode: `git diff main...HEAD --stat` and the full diff, plus `git log` on your branch.

**What good looks like.** Every hunk in the diff is legible as part of the one fix: a reviewer could point at any line of the diff and say why it's there. Debris tells itself: a commented-out line or block, a debug `print`/`eprintln` left in, a function marked `dead_code`/unused, a `TODO` on an unrelated line, a pure reindent/formatting hunk with no logic change, or an import/rename that rides along without being the fix. Commit messages like "wip," "fmt + cleanup," or "misc cleanups while debugging" are a tell to look harder at the diff, not a fact to grade on their own. None of this is forgiven by the core fix being correct and well evidenced elsewhere in the same PR — debris is graded on its own presence, not weighed against the fix's quality.

## Standards and comms (harness category: standards-wall)

**Where it lives.** In an eval bundle: the repo-facts block's stated PR-template sections, its contribution policy, and its AI-use disclosure policy, read against the candidate PR description's actual content; the thread highlights' explicit maintainer direction, read against whether the description engages it. In live mode: Path Review's `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`, read against your draft `pr_draft.md`, and the live issue thread.

**What good looks like.** Every section the template asks for has real, specific content — a "Testing" section that says what was tested and shows it, not a bare checkbox; a "Summary" that names the actual change, not "fixes the bug." Any repo-specific required item named in the repo's own docs (a `Closes #` link, a checklist, a changelog/whatsnew entry) is present in the diff or description, not just implied. If the repo's stated policy requires disclosing AI assistance, the description discloses it plainly — an otherwise excellent PR that skips a required disclosure still fails this check. Separately, if a maintainer left explicit direction or an open question in the thread, the description should engage it (confirm it was followed, or say why not) rather than reading as if the thread were empty. (Whether the description's own claims match the diff is plan fidelity, above — this family is about the repo's and the thread's asks, not internal consistency.)
